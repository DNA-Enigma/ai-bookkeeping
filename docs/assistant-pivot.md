# 参赛作品改造评估：从「记账 APP」到「端侧 AI 助手 + 记账」

> 2026-10-24 写。目的：把「改成 Today 那样的端侧助手」这个想法，变成一份能对着打分表
> 逐项核对的判断——哪些是真优势、哪些是错觉、缺什么、还剩多少时间。
> 本文所有结论都有可复现的命令；没有命令支撑的一律标了「待验」。

## 0. 一句话结论

**方向可行，但「复刻 Today」会直接输掉 20 分的模型核心贡献项。**
正确的改法是**保留 Today 的形态、放弃 Today 的架构**：Today 的主动智能靠用户把
邮件/日历/健康等 8 个服务的数据交给云端；端侧助手只能靠不离开手机的数据——
而账本恰好是手机上**结构化程度最高、连续性最强、因果链最完整**的那份数据。
记账不是助手的功能之一，是端侧助手**唯一拿得出手的主动燃料**。

## 3. 为什么「复刻 Today」是错的

Today 的真实架构（据 today.ai / 商店页 / 产品文档，非二进制逆向——标为**推断**）：

- 执行跑在云端常驻机器上，手机只是入口 + 通知出口
- 主动能力依赖用户**交出**邮件、日历、健康、消息等 8+ 个连接器的数据
- 断网即失能；数据全部出设备

把这条路线搬进比赛，等于主动放弃：

| 评分项 | 丢掉的分 |
|---|---|
| 端侧特性 25 | 云端执行 → 离线/隐私/时延三项全空 |
| 模型核心贡献 20 | 核心智能在云端，端侧模型沦为可替换模块（规则原文明文禁止） |

**45 分，这是结构性失分，不是发挥问题。**

而 Today 形态里**真正值得抄的只有两件事**：主动（不等用户开口）+ 记忆（跨会话不失忆）。
这两件事端侧完全做得到，且我们自己手里已经有燃料。

## 4. 重写后的定位

> **一个不联网也能主动的端侧助手。它知道你上周在吃上超了，今天周五，所以晚饭前提醒你。**

三个支点，每个都能落到已有代码上：

1. **主动的燃料是本地的**——账本 + 预算已经在 Room 里，不需要用户授权任何云端连接器。
   这是 Today 拿不到的：它要主动，必须先说服用户交出邮箱。
2. **隐私是可验证的，不是口号**——飞行模式下完整跑一遍，就是最硬的演示。
3. **双模型分工是天然的分项证据**——规则明写可两款结合使用：
   1.7B 走高频快路径（记账解析、意图判定，要低时延），4B 走低频重推理
   （周度复盘、异常检测、计划生成）。分工理由用 `SparkBatchActivity` 实测出来，
   正好命中「替换对比/消融佐证」。

## 5. 分期（17 天，按天算）

| 阶段 | 内容 | 产出证据 | 估时 |
|---|---|---|---|
| **P0** | 4B 真机 smoke：能否在目标机加载、首 token 多久、峰值内存 | 真机日志 + 内存曲线；跑不通就砍掉双模型，只保 1.7B | 1 天 |

| **P2** | 主动链路：`AlarmManager`/`WorkManager` 触发 → 短时前台服务 → 通知 | 冷启动被杀后仍能触发的实测；`BOOT_COMPLETED` 重排 | 4 天 |
| **P3** | 助手形态：把现有 chat 提升为首页，记账作为能力入口 | 界面改动：构建绿 + 单测 + 模拟器 | 3 天 |

留 2 天缓冲。**P0 是前置判断点**——4B 跑不动的话 P4 要重写，不能拖到最后才发现。

### 主动链路的技术口径（这条不要改）

Android 15 起 `dataSync` 前台服务**每 24 小时上限 6 小时**，「常驻前台服务保活」是死路。
正确拆法：

- **定时触发**：`AlarmManager.setExactAndAllowWhileIdle` 或 `WorkManager`
- **长任务**：短时前台服务，做完就退（现有 `ModelWorkService` 已是这个形状，复用）
- **App 被杀后仍要触达**：厂商推送（小米/华为/OPPO/vivo）——**需要你自己去各家开放平台
  注册拿 AppID/AppKey，我替不了**
- **保活补充**：开机自启 + 引导用户关电池优化（一个说明页，不做黑科技）

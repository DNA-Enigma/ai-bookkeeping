# 真实账单格式分析（2026-10-06，项目经理解析）

来源：用户导出的两份真实账单。以下每一项都是实际解析验证过的，不是推断。

## 1. 支付宝：`/home/dzsun/文档/支付宝交易明细(20260706-20261006).csv`

- **编码：GBK**（`file` 报 Non-ISO extended-ASCII；utf-8 解码失败，gb18030 成功）
- **换行：CRLF + LF 混用**
- 规模：596 笔记录，全文件 620 行
- 结构：前 23 行是回单头（导出信息、收支汇总、8 条特别提示），第 22 行是
  `----支付宝支付科技有限公司  电子客户回单----` 分隔线，**第 24 行（index 23）才是表头**：

```
交易时间,交易分类,交易对方,对方账号,商品说明,收/支,金额,收/付款方式,交易状态,交易订单号,商家订单号,备注,
```

- **表头尾部有多余逗号**（第 13 个空字段）
- 数据行示例（CSV 逗号分隔，字段内无引号包裹情况需注意商户名含逗号的风险）：

```
2026-07-06 11:48:25,餐饮美食,腊汁肉夹馍,157******21,经营码交易,支出,6.00,花呗,交易成功,2026...0959\t,1783...\t,,
```

- **坑：交易订单号/商家订单号字段尾部带 `\t`**（导出脏数据，入库前要 trim）
- **收/支 三档**：`收入` / `支出` / **`不计收支`**（充值、提现、账户转存等；回单头统计行
  也单独列了"不计收支：34笔"）。解析器必须处理第三档——不该记为支出或收入。
- 金额格式：`6.00`（两位小数字符串）
- 交易状态：`交易成功` 等（应过滤非成功状态，需确认有哪些取值）
- 字段顺序对应：交易时间, 交易分类(=支付宝的一级分类，可作科目参考), 交易对方(商户),
  对方账号, 商品说明(=明细行来源!), 收/支, 金额, 收/付款方式(=支付方式), 交易状态,
  交易订单号(=外部流水号), 商家订单号, 备注

> 注意：`商品说明` 列就是明细描述（如"经营码交易""哈啰单车卡抵扣骑行费用"），
> 这正是 ReceiptFields items 想要的东西——流水导入这边天然有。

## 2. 微信：`/home/dzsun/下载/微信支付账单流水文件(20260706-20261006)_20261006220212.xlsx`

- **格式：xlsx（Excel 2007+），不是 CSV，也没有加密 zip**。
  现有 `StatementImporter`（ZipCrypto 解密 + CSV 解析）**管不了这个格式**——
  需要新增 xlsx 读取路径（纯 JVM 可用 Apache POI 或轻量的 fastexcel/exp4j 类库，
  注意 core/statement 要保持纯 JVM 可测，别引 Android 依赖）。
- 规模：89 笔（收入 20 / 支出 61 / 中性 8）
- 结构：前言若干行（微信昵称、起止时间、导出类型、笔数统计、4 条注释），
  分隔线 `------微信支付账单明细列表------` 之后是表头：

```
交易时间, 交易类型, 交易对方, 商品, 收/支, 金额(元), 支付方式, 当前状态, 交易单号, 商户单号, 备注
```

- **收/支 三档**：`收入` / `支出` / **`中性交易`**（充值/提现/理财通/零钱通/信用卡还款）。
  与支付宝的"不计收支"同义，导入映射要统一处理这两第三档命名。
- 金额形如 `1941.90`，前言里带"元"字样，数据行需实测确认是否带 ¥ 符号（解析时兜底 strip）
- 时间均为 UTC+08:00

## 3. 对现有导入管道的影响（结论）

1. 格式配置按真实表头列名定稿，两份表头如上——**逐字照抄，不要用检索推断的列名**
2. 需要支持：GBK 编码检测、跳过回单头到分隔线/表头行、尾逗号、字段 trim `\t`
3. 需要新档位：不计收支 / 中性交易 → 建议不落账或落为"不计收支"标记，**不参与收支统计**
4. 需要新增 xlsx 输入格式（微信账单），与现有 zip+csv 并列
5. 样本文件在原路径，可直接拿来做测试夹具（**注意：真实账单含用户姓名/手机号/交易记录，
   属于隐私数据，只进本地测试，不得上传、不得提交进公开仓库**——测试夹具应合成脱敏样本，
   从真实文件提取格式规则即可）

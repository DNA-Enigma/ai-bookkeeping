## 现象 A：`POST /v1/tasks` 阻塞 150 秒以上，任务停在 `planning`

实测（隔离实例 8025，模型 `qwen-3.8-max`，带 174KB 账单图）：

```
curl -s -m 150 -X POST http://127.0.0.1:8025/v1/tasks ... -w "HTTP %{http_code} %{time_total}s"
→ HTTP 000 150.004400s        # 客户端超时，服务端仍在跑
GET /v1/tasks?limit=3 →
  "task_id":"task_705366f7f4ba4a759902","status":"planning",
  "title":"评估器未能完成，使用兜底画像。","task_type":"generic.unknown"
```

- 契约里 `limits.sync_timeout_ms = 8000`，超过应**提升为异步**并返回 `202 + mode_changed:true`（见 `openapi.yaml` `/tasks` 的 description）。实测 150 秒仍是 `mode:"sync"`、`status:"planning"`，**超时根本没生效**。
- 根因方向：`pipeline.submit()`（`dispatcher/pipeline.py:562`）在 `stop_after_planning=True` 时**同步跑完评估+路由+拆解**才返回，这段耗时不受 `sync_timeout_ms` 约束；该值只作用于"拆解之后执行"的投影。

## 现象 B：致命 LLM 错误逃逸成纯文本 500

实测（隔离实例 8023，模型 `GLM-5.3-Flash`，同一条请求）：

```
HTTP 500
Internal Server Error        # 21 字节，不是 problem+json
```

服务端栈：`dispatcher/adapters/openai_compat.py:216 → raise last`（`LLMError: 供应商 400（请求被拒）`）→ 经 `decomposer._freeform` 判定 `fatal` 后 re-raise → `dispatcher/interface/app.py:478 create_task` **没有任何异常映射** → Starlette 默认 500。

- 契约要求错误体是 `application/problem+json`，`upstream_llm_error` 映射为 502（`dispatcher/core/errors.py:30` 已有映射表）。
- 所以问题不在错误分类，而在**接口层没有兜底**：凡是 planning 阶段抛出的 `DispatcherError`/`LLMError`，都应走 `core/errors.py` 的映射，而不是让 Starlette 吐纯文本。

## 要做的事

1. **planning 阶段纳入超时**：`submit()` 的同步段（评估/路由/拆解）要有墙钟上限，超时即返回 `202 + mode_changed:true + mode_change_reason`，任务转后台继续；上限取 `min(limits.sync_timeout_ms, envelope.constraints.max_wall_ms)`。
2. **接口层异常兜底**：`create_task`（及所有端点）捕获 `DispatcherError`/`LLMError`，用 `core/errors.py` 的 `status/code/title` 映射成 `problem+json`；未预期异常也要返回带 `code` 的 500 problem+json，不许出现裸文本。
3. 不要为此引入后台队列/新依赖；用现有的任务状态机与 `asyncio` 即可。

## 禁止

- 不许把 `sync_timeout_ms` 直接调大来"绕过"（那是掩盖）。
- 不许改现有测试用例；不许改 `.env`；测试不许依赖外部 LLM（用 `tests/fakes.py`）。
